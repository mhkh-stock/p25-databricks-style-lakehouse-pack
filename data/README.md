# P25 — Data dictionary + known quirks

## The source files — `data/raw/` (SAMPLE)

SAMPLE files for the fictional wholesale distributor **Ravi Traders,
Lahore**, Wed 2026-07-01 → Thu 2026-12-31 (6 months, 184 days).
Generated by `src/generate_data.py` (seed 20261121). 520 sale lines,
160 purchase lines, 36 products, 22 shops, 7 suppliers.

### `sales_SAMPLE.csv` — 520 lines (512 clean + 8 planted defects)

| Column | Type | Meaning |
|---|---|---|
| order_id | text | `ORD-0001` …; an order can have several lines |
| sale_date | text | `yyyy-mm-dd`; the sale day |
| shop_id | text | `SHP-01` … `SHP-22`; the shop that bought |
| product_code | text | `PRD-001` … `PRD-036`; must exist in the product master |
| qty | integer | Units sold on this line (must be > 0) |
| unit_price_pkr | integer | Sell price per unit in PKR (from the product master) |
| line_total_pkr | integer | Must equal `qty × unit_price_pkr` |

**Planted defects (8 lines, found exactly by the DQ tests):**

File line numbers count from the top of the CSV file (header is line 1).
`raw_line_no` in the lakehouse is the data-row number = file line − 1.

| Defect | Lines | Detail |
|---|---|---|
| Exact duplicate lines | 2 | File lines 140 & 281 are the same line (ORD-0059, PRD-026, qty 39, PKR 20,280); file lines 156 & 458 are the same line (ORD-0063, PRD-030, qty 13, PKR 64,350). Silver keeps the first occurrence. |
| qty ≤ 0 | 3 | Line 50 (ORD-0208, PRD-025, qty 0, PKR 0); line 131 (ORD-0210, PRD-019, qty −3, PKR −9,450); line 171 (ORD-0209, PRD-017, qty −1, PKR −6,300). |
| Unknown product | 2 | Line 206 (ORD-0211, product PRD-997); line 317 (ORD-0212, product PRD-998). Neither code exists in the product master. |
| Wrong line total | 1 | Line 511 (ORD-0213, PRD-035, qty 9 × PKR 3,000 = PKR 27,000, but recorded as PKR 27,750 — PKR 750 too high). |

The raw gross of all 520 lines is PKR 16,261,690. The clean gross of
the 512 silver lines is PKR 16,155,060 — the PKR 106,630 difference is
exactly the 8 rejected lines (PKR 20,280 + 64,350 duplicates,
PKR 0 − 9,450 − 6,300 bad quantities, PKR 10,000 unknown products,
PKR 27,750 wrong total).

## Reference lists (not CSVs — loaded from `sql/gold_dimensions.sql`)

The shop and supplier masters are small reference lists the client
keeps outside the transaction exports, so they live as VALUES in the
dimension loader, not as CSVs:

- **dim_shop** — the 22 shops Ravi Traders supplies (SHP-01 …
  SHP-22, name + area in Lahore).
- **dim_supplier** — the 7 suppliers (SUP-01 … SUP-07, name + city).
  One supplier, Punjab Tea & Dry Fruit Traders, supplies two
  categories (Tea & Beverages and Dry Fruits & Nuts).

## Known quirks (read before quoting a number)

- **The 9.44% margin is a wholesale margin, not a retail one.** Ravi
  Traders is a distributor: thin margins on high volume. Gross profit
  uses the product master's standard cost price, not the per-PO unit
  cost (which moves ±3% around it) — so profit is the margin on the
  price list, not on each individual purchase.
- **November looks like the best month (PKR 3,454,030) and December the
  weakest (PKR 1,328,550, only 42 lines).** That is the sample's own
  pattern, not a finding about the real market — December simply drew
  fewer orders in this seeded sample.
- **Honey (1 kg jar) is the top product by sales (PKR 1,097,250)** — a
  high-ticket, low-volume line, not the highest-volume one. Flour &
  Atta moves the most units (1,480) at the lowest ticket.
- **Every purchase order has exactly one line in this sample.** So
  `po_count` and `po_lines` are the same number (160) — on a real
  client file with multi-line POs they will differ, and the mart is
  written to count them separately.
- **dim_product is SCD Type 1.** A price change overwrites the old
  price; no price history is kept. If the client later needs history,
  the dimension becomes Type 2 (`valid_from` / `valid_to`) — the
  loader is the only file that changes.
- **This is Databricks-STYLE, not Databricks.** See
  `databricks/mapping.md`: no workspace, no .dbx file, no Delta Lake
  file exists in this repo. Delta MERGE / OPTIMIZE are Databricks-only
  and are simulated here in SQL.
